# API protette per agenti — 20 novembre 2026

Branch `feature/protected-agent-api`, derivato da `a408e0e`. Nessuna modifica locale preesistente delle notifiche o dell'anagrafica CER inclusa. Destinazione autorizzata: Jarvis Docker, non QA SiteGround.

## Accesso e gestione

**Anagrafiche → Agenti e token API**, `/dev/agents`: solo utenti con ruolo `developer`, anche per scritture, emissione e revoca. Il flag amministratore da solo non concede accesso. Gate `manageAgents` e menu coerenti.

Identità tecniche nella tabella `agents`, separate dagli utenti umani; autenticazione Sanctum 4.4 con Bearer obbligatorio e nessuna autenticazione via sessione browser. I token non autenticano le pagine web o le vecchie API a sessione. I permessi devono essere presenti sia sull'agente attivo sia sul token. La rimozione di un permesso sull'agente ha effetto anche sui token esistenti.

Il developer crea identità e permessi, emette un token nominato con validità 1–365 giorni (default UI 90), copia il segreto mostrato soltanto nella risposta di emissione e lo custodisce nel servizio agentico. Nessun segreto in props Inertia, cronologia di pagina, repository, prompt o metadati token; solo hash in database. Risposta di emissione `no-store`; revoca immediata per singolo token e disabilitazione dell'agente per tutti i suoi token. Per la rotazione: emettere nuovo token, aggiornare il servizio, revocare il precedente. Pulizia giornaliera dei token scaduti da almeno 24 ore.

Il pannello espone solo metadati dei token, mai hash o valore originale. La UI emette token con tutti i permessi attuali dell'agente; il backend di emissione supporta anche un sottoinsieme. Registrati eventi amministrativi con attore umano, permessi/stato dell'agente e ID token, senza segreti.

## Contratto HTTP

Prefisso `/api/v1`, risposte JSON anche quando `Accept` manca. Limite 60 richieste/minuto per agente; le richieste non autenticate non accedono ai dati. Ogni agente autorizzato alla lettura accede ai dati del gestionale per quella capability: non esiste un isolamento per cliente o mailbox implicito.

| Risorsa | Metodi |
| --- | --- |
| `/orders` | GET paginato, POST atomico con `items` e `holders` |
| `/orders/{order}` | GET dettaglio, PATCH |
| `/orders/{order}/items` | GET, POST |
| `/orders/{order}/items/{item}` | GET, PATCH, DELETE reversibile nel dominio |
| `/journeys` | GET paginato, POST piano |
| `/journeys/{journey}` | GET dettaglio, PATCH piano |
| `/references/{resource}` | GET paginato con ricerca, capability `reference:read` |

Anagrafiche consentite: customers, sites, cer-codes, holders, vehicles, trailers, cargos, warehouses, drivers, technical-actions. Nessun elenco utenti generico o endpoint pubblico di emissione token.

Capability: `reference:read`, `orders:read/create/update`, `journeys:read/create/update`. Le operazioni sui materiali richiedono `orders:update` e verificano l'appartenenza all'ordine padre. Nessun permesso jolly emesso dal pannello.

```http
Authorization: Bearer <TOKEN_DAL_GESTORE_SEGRETI>
Accept: application/json
Content-Type: application/json
Idempotency-Key: <UUID_DELL_OPERAZIONE>
If-Match: <VERSIONE_LETTA_CON_GET>
X-Agent-Run-Id: <RIFERIMENTO_OPACO_OPZIONALE>
X-Source-Reference: <RIFERIMENTO_OPACO_OPZIONALE>
```

`Idempotency-Key` obbligatoria su tutte le scritture (8–200 caratteri): una richiesta identica restituisce il risultato precedente, con `Idempotency-Replayed: true`; riutilizzo per payload/percorso/metodo/versione differenti → 409. Chiavi isolate per agente, condivise tra i suoi token. Il risultato contiene gli stessi dati operativi già restituiti dall'API e resta memorizzato nel database privato: nessuna auto-purge delle richieste introdotta.

`If-Match` obbligatorio per aggiornamenti e mutazioni dei materiali, incluso POST di una riga. Usare `data.version`, `order_version` oppure ETag del GET; versione superata → 409, header mancante → 428. Le versioni includono contenuto corrente e associazioni, quindi rilevano anche modifiche dalla UI.

PATCH ordine conserva le liste omesse; `items`/`holders` presenti sostituiscono l'intera lista, con array vuoto che la svuota. PATCH viaggio conserva i campi omessi; ogni ordine selezionato deve essere presente in una sola tappa. ID negli esempi Swagger dimostrativi, da recuperare tramite le anagrafiche.

## Dominio e compatibilità UI

`OrderWriter` e `JourneyWriter` sono condivisi con i controller web della logistica: nessuna simulazione di richieste web da parte delle API. Conservati redirect UI e generazione/invalidazione documenti. Transazioni, lock, prenotazione ordini e guardie contro cambi del piano dopo la partenza; controllo di configurazione motrice/cassoni/rimorchio condiviso. I controlli condivisi di configurazione non equivalgono a un nuovo motore completo di ottimizzazione o di verifica dimensionale del carico.

Validati cliente/sede, riferimenti anagrafici, appartenenza dei materiali/gruppi, HP/ADR e magazzino; un cliente senza commerciale dotato di codice produce un errore di validazione anziché un errore PHP. Preventiva verifica degli ordini già assegnati e prenotazioni transazionali impediscono di spostare ordini da un altro viaggio.

Audit di dominio attribuito all'identità Agent anche quando il client presenta contemporaneamente cookie web. Le versioni legacy con solo `user_id` non attribuiscono l'ID agente a un omonimo utente umano; la tracciatura completa è in audit polimorfico e `agent_api_requests`.

**Queste API applicano dati operativi direttamente quando il developer concede la capability di scrittura.** Non implementano il workflow email di bozza/proposta/approvazione né gruppi atomici di microvariazioni già discussi in `laravel_platform_updates.md`: per un agente email con quelle regole non concedere scritture generiche prima di introdurre le relative operazioni dedicate. I viaggi partiti/chiusi non si modificano tramite questi endpoint di pianificazione.
